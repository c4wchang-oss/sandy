---

**Tweet 2**
Skill 就是你自己寫的 Markdown 文件。

你定義團隊的慣例：先搜尋哪個 library、variable 命名規則、要用哪些 component、auto layout 的結構邏輯、什麼時候要做 accessibility 檢查。

Agent 在每個任務開始前都會讀一遍。不是偶爾。每次。

---

**Tweet 3**
這跟一般 prompt 不同。

Prompt 每次任務都要重寫。它會漂移。它會被忘記。它取決於當下在場的人。

Skill 是機構性的。永久的。按需執行——不需要你在場。

---

**Tweet 4**
Figma 的說法很清楚：「Design system 給 agent 對的 component。Skills 把團隊的其餘專業疊加上去。」

這就是我一直在找的分界線。

System = 用什麼來 build。
Skill = 在 build 的過程中怎麼思考。

---

**Tweet 5**
「Constraint architecture」是我幾個月來描述這件事的方式。

Skills 是我看過最明確的形式。你把限制寫進 .md 文件。Agent 在每個任務開始前都讀進去。

你的判斷，被一致執行，在規模下。

---

**Tweet 6**
沒人在說的資深設計師意涵：

這是一種新的可交付成果。不是 spec，不是 component，是 agent 的課程大綱。

如果你沒辦法把團隊慣例寫得夠清楚讓機器跟隨，你對它們的理解還不夠深。

---

**Tweet 7**
誠實地說：寫好 Skill 本身就是一個新技能。

含糊的 Skill → 含糊的輸出。
通用的指令 → 通用的結果。

工作量在於精確度的寫作。這是一種大多數設計師沒受過訓練的紀律。

---

**Tweet 8 (CTA)**
真正的標題不是「Figma 的 agent 變聰明了」。

是「你有了一份新工作：寫課程大綱，而不只是 spec」。

從這裡開始 → 為你最常用的工作流程寫一個 Skill。如果你寫不清楚，那就是你的設計運營債在現身。
