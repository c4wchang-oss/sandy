**Tweet 1 (Hook)**

「有規則的精靈比有想像力的精靈更有用。」

這是 GenieUI 的 tagline。

也是迄今最準確描述 AI design tool 應該怎麼運作的一句話。

🧵 1/8

---

**Tweet 2**

GenieUI 從自然語言 prompt 生成 iOS 和 Android 介面。

但 model 不能隨意發明 HTML 或 CSS。

它只能從你登記的 design system 裡選 component、配置、排版。

你的 component catalog 是精靈的邊界。

2/8

---

**Tweet 3**

Output 不是 screenshot。
也不是你要花一個小時清理的任意 HTML。

是一個 component tree——有 views、layers、inspector、zoom 和直接操作。

因為全部都從你的 component 生成，所以所有東西都是可編輯的。

3/8

---

**Tweet 4**

大多數 AI design tool 的邏輯：

自由生成 → 你去修 → 事後套上限制。

GenieUI 反過來：

先登記你的 design system → model 在你的 catalog 內選擇 → output 一開始就符合。

這是在 generation 這一步做 constraint architecture，不是在 cleanup 那一步。

4/8

---

**Tweet 5**

GenieUI 也是 model-agnostic 的。

Claude、Codex、Gemini、Grok、DeepSeek、Mistral——可以針對不同任務換 model，不需要重建 project。

沒有 vendor lock-in，就沒有任何單一 model 的美感偏見固化在你的工作流裡。

5/8

---

**Tweet 6**

Quality ceiling 是你的 design system 詞彙量。

Component props 模糊 → output 模糊。
Token 命名不一致 → layout 不一致。

Brief bottleneck 沒移動。Execution bottleneck 移動了。

GenieUI 讓你以前可以忽視的 design system 債，現在會直接顯形。

6/8

---

**Tweet 7**

誠實說的部分：

GenieUI 是社群 v0.1 項目。
「component tree」到「deployed mobile screen」之間還有 gap。
它不是要取代 Figma 或你的 design system 工具。

但 constraint-first 架構是對的。
接下來做到 production quality 的那個工具，就是贏家。

7/8

---

**Tweet 8 (CTA)**

比較難的 design system 問題不是「我們有沒有 component？」

是：「我們的 component props、token 名稱和文件，是不是具體到足以讓 agent 在不問你的情況下做好決定？」

如果不是，那是 design system 的問題——不是 AI 的問題。

8/8
