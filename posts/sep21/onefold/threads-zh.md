你部署的和你想要的之間的落差，現在對 AI 是可見的了。這是 Onefold 讓人不舒服的部分。

Onefold 掃描公開網站，產生 DESIGN.md：一個放在程式碼旁邊的純 markdown 文件，告訴 coding agent 你的顏色、字型、深色模式邏輯、圓角半徑、陰影、component 函式庫選擇、語氣指南，和要避免的 pattern。跟 AGENTS.md 對工程慣例的角色一樣。設計端終於有了對應的東西。

限制架構堆疊已經在沒有人協調的情況下建立好幾年了：AGENTS.md 管程式碼，然後是 CLAUDE.md 管 agent 行為，然後是 Vercel 的 design.md 格式（9 月 2 日），然後是 R/GA 的 BRDNA Sequencer 把品牌 DNA 轉換成 agent 情境（9 月 19 日）。Onefold 是自助服務版本——它讀取已部署的內容，自動產生文件。

我一直在回頭想的誠實讀法：Onefold 萃取的是部署了什麼，不是想要什麼。每個沒有文件記錄的例外。每個不在設計系統裡的一次性顏色。每個在三次改版中漂移的圓角半徑。AI agent 會把這些全部繼承為「品牌標準」。這跟 9 月 Webflow 自動產生 Agent Instructions 的情況一模一樣——誤打誤撞成為整個生態系統中最好的設計債務鑑識工具。Onefold 是同一件事，往上游移了一層。

我真正會推薦的工作流程：先跑一次，讀它找到了什麼，把輸出當成設計債務稽核報告而不是完成的文件，決定哪些是刻意的、哪些是漂移累積的，先在實際設計系統裡修正漂移，然後再讓 agent 指向清理過的文件。他們操作指南的第七步——「對照文件和實際產品審查下一個產生的畫面」——是大多數人唯一會跳過的步驟。不要跳過它。

一個誠實的說明：品質天花板不會因為 Onefold 而移動。它解決的是啟動阻力問題。啟動阻力是真實的——大多數團隊沒有寫 DESIGN.md，因為明確表達設計意圖是一項不舒服的工作，一直被放到優先事項的後面。Onefold 解決了這個問題。你的品牌到底代表什麼的判斷，還是你的。

自己寫好的 brief 很有用。你還是必須審查它。
