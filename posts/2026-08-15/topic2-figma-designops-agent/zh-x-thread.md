# Topic: Figma AI agent 實際測試證實其稽核/維護優勢，以及創建方面的差距 (Aug 2026)
# Platform: X (Twitter)
# Format: 8-tweet thread

---

**Tweet 1 — Hook**
幾個月的 Figma AI agent 實際測試，得出了一個很明確的結論。

它不是大家期望的 design system 建造者。

它是一個目前更實用的東西：design system 的清潔員。

這對你的角色意味著什麼。🧵

---

**Tweet 2**
它做得好的事：
- 稽核不符合命名規則的 variable
- 標記 detached component 和 hardcoded 數值
- 大規模撰寫 component 文件
- 系統的 gap analysis
- 發布前的一致性檢查

---

**Tweet 3**
它吃力的事：

創建忠實於你既有系統 pattern 的新 component。

不是因為模型不夠好。

而是「忠於你的系統」需要只有你才建立起來的 context。

---

**Tweet 4**
這個分野很重要。

結構化、可重複的分析性工作，AI 做得很可靠。

在系統限制內發明——沒有足夠深的 context——AI 會產生偏移。

前者可以 scale。後者需要人監督。

---

**Tweet 5**
對 senior designer 的意義：

你的工作不再是維護。

你的工作是建立一個「足夠讓 AI 維護」的系統。

命名、文件、auto layout、component properties——現在是你的 AI context 參數。

---

**Tweet 6**
「足夠清晰」在實務上代表：

- 語意化的 variable 名稱（不是「Blue-300」）
- Component 說明要解釋「何時用」，不只是「長什麼樣」
- 所有東西都加 auto layout——這是 agent 理解空間意圖的方式
- Component properties 定義每個狀態

---

**Tweet 7**
一個實用的 review 分層框架：

低風險：文案、間距、小視覺修改 → AI 審查，不需要批准
高風險：新 component、結帳流程、無障礙敏感 pattern → 需要人類簽核

設計審核的關卡。不是盯著每個像素。

---

**Tweet 8 — CTA**
Design system 不再只是一個 library。

它是你的 AI agent 運作的 context window。

你的發布標準和你的 AI 品質標準，剛剛變成了同一份文件。
