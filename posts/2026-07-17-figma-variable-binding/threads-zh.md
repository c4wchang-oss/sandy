# Threads 貼文 — Figma Variable 自動綁定（繁體中文）
**格式：** 長篇個人觀察，不加 hashtag

---

昨天有一個 Figma 的 release note 幾乎沒有人在討論，但它悄悄修好了設計系統工作裡最昂貴的其中一個問題。

這個功能：當你把程式碼畫面帶進 Figma canvas 時，顏色、字型、間距現在會自動綁定到你檔案裡已有的 variable，而不是以硬編碼的值落地。

這聽起來像是一個方便的小改進。但它實際上是一個架構上的轉變。

多年來，設計與程式碼之間的雙向循環在一個方向上是壞掉的。Token 從設計流向程式碼很順暢 — 那個方向已經跑得不錯一段時間了。但要把任何東西*從程式碼帶回* Figma，意味著接受一堆硬編碼的 hex 值、直接的像素大小，以及一個完全不存在的 token 結構。清理成本太高，大多數團隊直接放棄了。程式碼畫面留在 dev 端，設計畫面留在 Figma，兩者之間的落差不斷擴大。

那個落差，就是不一致性滋生的地方。那個落差，就是「設計說 X 但程式碼做的是 Y」的對話發生的地方 — 那種吃掉你一半 sprint retrospective 時間的對話。

現在，有了匯入時的 variable 自動綁定，方向是真正雙向的了。把 AI 生成的畫面、舊的程式碼畫面，或任何來自 dev 環境的東西帶回 Figma — 你設計系統的 token 層在這個過程中能夠存活。

我一直在思考的框架是：你的 constraint 架構現在對 AI 生成的輸出具有韌性了。當你用 AI 工具生成畫面 — Figma Make、Cursor、或外部工具 — 輸出以前在到達時就會破壞你的 token 結構。現在它會綁定。你花了好幾個月建構的設計系統，不再是 AI pipeline 能夠在匯入時意外拆散的東西了。

我最直接興奮的使用場景其實不是 AI 的角度 — 而是舊畫面的還原。我待過的每個產品都有只存在於 dev 端的畫面：建構得很正確、在程式碼裡符合 token 規範，但因為重建成本太高，從來沒有在 Figma 裡被文件化。那是一個設計系統治理的問題。而它剛剛變得容易解決多了。

這是系統設計的勝利，不只是一次功能發布。雙向循環修好了。
