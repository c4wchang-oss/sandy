Figma 這週上線的東西，讓我一直在想的不是 Code Layers 或 Specs——是 Payload。

Payload 是一個 backend：資料庫、檔案儲存、使用者驗證、後台管理面板、API，全部在 Figma Make 裡面。你描述一個 app，Figma 幫你建好，現在內容管理系統也一起來了。你的行銷同事透過內建後台更新文案。文案同事發佈文章。設計師控制什麼是鎖定的。

表面的故事是「Figma Make 的 no-code CMS」。更深的故事是「交付」這個概念發生了什麼。

我們幾個月來一直在追這件事的發展。Figma Code Layers（設計→工作程式碼在畫布上）+ Figma Specs（Agent 的 brief 層，畫布上的多人 Markdown）+ Payload（後端 + CMS，也在畫布裡）= 設計檔案不再是產品的描述。它就是產品。

沒人準備好的治理問題：當一個工具同時控制設計系統、內容 schema 和 production 部署，誰對什麼有審核權？設計檔案裡改了一個顏色 token——會不會 cascade 到線上環境？內容發佈前誰負責審查？這把兩個一直分開的治理領域壓縮在一起了。

對資深設計師來說，角色轉移是真實的。你不再在設計交付物了。你在設計權限架構——誰可以改版面？誰可以更新文案？誰可以發佈？那是基礎建設設計。它剛好住在你的設計工具裡。

誠實說明：這還是 beta。託管只在美國。GitHub / 本地開發工作流程還不存在。對有真正複雜度的正式對外產品，還沒準備好。但對內部工具、行銷網站、需要非技術團隊管理內容的早期原型？這是對的範圍，Payload 處理得很乾淨。

「從原型到生產」這個承諾已經說了幾年了。Payload 是第一個讓它感覺是架構上真實、而不只是願景真實的東西。問題不再是 Figma 能不能做到。而是你的團隊的設計治理，能不能跟上這個工具現在能做到的事。
