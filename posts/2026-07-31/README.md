### Topic 1: Maze AI Conversation Block
**Source:** https://maze.co/blog/ai-conversation-block/ (July 2026)

**Core Insight:** Unmoderated research has always had one hard constraint: you catch *what* people do, never *why* — at least not in the same session. Maze AI Conversation Blocks put adaptive follow-up questions right after any interaction, while the friction is still in working memory. The two-phase research sprint (behavioral study → qualitative follow-up) just collapsed into one.

**Key Facts:**
- Insert AI conversation blocks anywhere in an unmoderated Maze study
- Adaptive follow-up questions based on participant responses
- Conditional logic: different questions for different people based on what they say
- Works alongside existing Maze AI: study builder, AI moderator, Maze MCP
- Combines behavioral data (paths, misclicks, ratings) + qualitative (why) in a single session

**Real Headline:** "Unmoderated research just got a 'why' layer. The what and the why are now the same session."

### Topic 2: Lovable App User Connectors
**Source:** https://lovable.dev/blog/app-user-connectors (July 29, 2026)

**Core Insight:** You build one app. Your users each bring their own data reality. Lovable's app user connectors let every end user connect their own Google, Slack, Salesforce, or HubSpot account — so the app runs on N personal data contexts, not one shared integration. This is constraint architecture at the user level: the designer no longer controls what data appears, the user's own permissions do. A familiar enterprise design challenge lands squarely in the no-code builder space.

**Key Facts:**
- Each end user connects their own third-party accounts (Google, Microsoft, Slack, Salesforce, HubSpot, etc.)
- Auth via Lovable's connector gateway — no user tokens exposed in the project
- Works for internal tools and products you sell
- One-time workspace setup → each user connects independently
- Shifts from shared integration → per-user, permission-gated data

**UX Implications:**
- Empty states become primary design flows (unconnected vs connected first-run experience)
- Error states become identity-specific (token expiry = this user's access to their data)
- Layout must hold across wildly different data sizes and shapes
- Designer becomes framework architect, not primary user

**Real Headline:** "The app you built now runs on data you can only partially predict. Does your design hold when the data isn't yours?"
