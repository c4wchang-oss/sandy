# Threads 貼文 — Claude Design + /design-sync（繁體中文）
**格式：** 長篇個人反思 + 有力的觀點
**語氣：** 有深度、無 hashtag、比 X 更個人化的反思

---

Anthropic 推出了 Claude Design。又一個 AI canvas。但我一直用錯誤的角度看這件事——我覺得大多數的評論也是。

有趣的不是那個 canvas。是一個叫 `/design-sync` 的命令，從 Claude Code 的終端機執行。你跑它，它讀取你的 codebase——你真實的元件、顏色 token、字型、間距——然後把那些匯入 Claude Design。現在你是針對你真實的設計系統生成，不是通用的 template。完成之後，你把它推回去：同一個命令，反方向，你的程式碼再次以可編輯的 canvas 形式出現。

這是我第一次看到有人從 codebase 那一側解決交付問題，而不是從設計那一側。

傳統的交付——設計師做檔案、匯出 spec、工程師重建、失去意圖、沒人再打開 Figma——存在是因為讓設計和程式碼保持同步的維護成本太高。同步一直是手動的、非對稱的、不斷退化的。你仔細標注、傳出檔案，然後看著設計意圖在 PR merge 的時候消散。

/design-sync 讓同步變成一個命令，不是一個維護工作。安全模型也很謹慎：Claude 生成一個計劃（它要寫什麼、要刪什麼、執行順序），然後等你批准。沒有任何事情是靜默發生的。

這對 Senior 設計師意味著什麼：籌碼的位置移動了。不是從 Figma 移到 Claude Design——那是表面的改變。是從交付文件移到餵給 sync 的設計系統。Token、元件 constraint、命名規範——那才是 /design-sync 讀取的東西。那才是會帶走的東西。那才是重要的。

交付文件一直是一個會造成資訊流失的翻譯層。如果設計系統是機器可讀的，而 sync 是雙向的，那個翻譯層就消失了。

這才是真正的標題。不是那個 canvas。
