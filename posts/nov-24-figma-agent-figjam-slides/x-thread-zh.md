**[Tweet 2]**
「完整 pipeline」實際上意味著什麼：

→ FigJam：附加設計檔案、逐字稿、研究筆記 → agent 把它們整理成一個 board，幫你把想法推得更遠
→ Slides：把材料變成 draft presentation，為不同受眾調整 deck，縮短全簡報的 copy
→ Design（canvas）：本來就有
→ Dev Mode：檢視設計、比較版本、取得程式碼片段、批量下載資產

FigJam 和 Slides 是兩個缺口。同一次發布，兩個都補上了。

---

**[Tweet 3]**
沒人會大聲說出的瓶頸：

不是設計執行。是 context 組裝。

十二份用戶訪談逐字稿。三個設計迭代。兩場不同會議的 stakeholder 筆記。六個月前的一份舊 deck。這一切需要變成一個有條理的 FigJam board，你才能跑真正的合成 session。

這是真實的時間成本。這正是 FigJam agent 現在在處理的事。

---

**[Tweet 4]**
Slides 的故事比表面上看起來更有趣。

「為不同受眾調整 deck」和「縮短整份簡報的 copy」——這些不是執行任務。這些是需要 audience modeling 的溝通設計決策。

Agent 現在在判斷工程副總裁需要看什麼、PM 需要看什麼。那不是搜尋替換，那是重新結構。

仔細觀察它在這件事上做得有多好或多差。Brief quality ceiling 在這裡的作用方式不一樣。

---

**[Tweet 5]**
輸入品質問題：

Agent 從你帶進來的東西工作。如果你的逐字稿分散在不同格式、三個不同工具裡，FigJam board 就會反映那種分散。

如果你的 slides deck 在你要求 agent「為新受眾調整」之前有 40 張沒有邏輯結構的投影片，調整後的版本就會有 40 張不同分散方式的投影片。

Garbage in，organized garbage out。輸入現在就是 brief。

---

**[Tweet 6]**
和 Dev Mode（11 月 19 日）比較：

Dev Mode agent：檢視設計、比較版本、索取程式碼片段、批量取得資產下載連結。

那是下游的、確定性的、可驗證的。Agent 讀取設計意圖並翻譯它。

FigJam + Slides 是上游的、詮釋性的。Agent 從 artifact 建構意義。那是不同的信任校準。錯誤模式更隱微。

---

**[Tweet 7]**
現在在所有付費方案上都可用。

值得注意：兩個產品的 connector 和 attachment 是有具體範圍的——設計檔案、逐字稿、研究筆記被明確列出。不是「附加任何東西」。

這是有意為之的範圍設定。Agent 讀取的是有結構的 artifact，不是任意檔案。那個範圍對品質很重要。

---

**[Tweet 8]**
重新框架：

Figma 不只是在兩個產品裡加了 agent 功能。他們在同一週封閉了設計流程 pipeline 的兩端：上游 context 組裝（FigJam）和下游 stakeholder 溝通（Slides），以及工程交接（Dev Mode）。

問題不是「agent 有沒有幫助？」幾乎肯定有。

問題是：你的研究 artifact 現在有多有結構？因為那才是決定這是節省時間還是整理時間的因素。
