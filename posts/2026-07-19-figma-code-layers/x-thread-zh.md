# X Thread — Figma Code Layers（繁體中文）
**主題：** Figma Code Layers（closed beta）——可執行程式碼作為 Figma canvas 上的圖層類型
**角度：** Canvas 吸收了程式碼。交接（handoff）消失了。設計與工程終於共用同一個產物。
**格式：** 8 則推文串

---

**Tweet 1（Hook）**
Config 2026 Figma 發布的東西裡，最重要的不是 motion，不是 shader。

是 Code Layers。

但幾乎沒人在談論它對設計團隊工作方式的真正意義。

讓我解釋一下。🧵

---

**Tweet 2**
Code Layers 實際上是什麼：

真實、可以執行的程式碼——作為 Figma canvas 上的一種圖層類型。

你把 GitHub repo clone 進來。它活在 canvas 上。它可以跑。你的團隊可以看到它、評論它、用提示語對它做修改。

不是截圖。不是預覽。是一個可以用的、可以編輯的圖層。

---

**Tweet 3**
改變一切的功能：「Extract designs（提取設計）」。

從任何程式碼圖層，你可以把當前狀態轉換回可編輯的 Figma 圖層。

你調整設計。一鍵把你的編輯更新回程式碼圖層。
完成後，把變更推回你的 repo。

設計 → 程式碼 → 設計 → 程式碼。同一個產物，同一個 canvas。

---

**Tweet 4**
十年來，設計和工程的協作是這樣的：

設計師在 Figma 工作。工程師在 IDE 工作。交接是他們交換產物的時刻。

每次交接都是一次翻譯——而翻譯會流失資訊。

Code Layers 把交接折疊進 canvas 裡。翻譯這一步消失了。

---

**Tweet 5**
這對設計師角色的意義很重大：

以前：你在工程師的工作「旁邊」設計。
之後：你在和工程師「同一個產物」上設計。

你可以在一個運行中的元件上標注、用提示語要一個變體、提取成設計圖層、調整細節、再推回去。

那不只是設計。那是同一個介面上的設計加程式碼審查。

---

**Tweet 6**
沒人說出口的不舒服的真相：

這個功能在 closed beta 是有原因的。不是每個團隊都準備好了。

如果設計師修改了一個程式碼圖層——誰擁有那個變更？誰審查？誰批准推回 repo？

這些不是工具問題。這是治理問題。沒有想清楚設計工程協作模式的團隊會很快撞上這些牆。

---

**Tweet 7**
我在觀察的事：

設計主管會開始在 Figma 裡 review 程式碼，而不是在 PR 裡嗎？

如果是的話，Figma 就不只是設計工具，而是工程審查介面。那是平台策略，不是功能更新。

Cursor、Copilot Workspace 和其他工具剛剛發現他們的護城河比想像的窄。

---

**Tweet 8**
真正的新聞不是「Figma 在 canvas 上加了程式碼」。

而是：Figma 在對「事實來源（source of truth）在哪裡」這個問題做出主張。

不是 IDE。不是設計檔。是共用的 canvas——程式碼和設計共存，兩個團隊都在上面工作。

這要嘛是天才，要嘛是混亂，取決於你的團隊是怎麼組織的。
