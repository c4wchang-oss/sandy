**標題：** Figma Code Layers：交接消失了。程式碼現在活在設計 canvas 上。

---

十年來，設計和工程一直平行運作——而交接（handoff）是他們痛苦嘗試同步的那一刻。

Figma Code Layers（目前在 closed beta）想要完全消滅那個時刻。

這是什麼、改變了什麼，以及你真正需要知道的事。

---

🔍 **Figma Code Layers 是什麼？**

Code Layers 是 Figma Design 中的一種新圖層類型。不是矩形或元件，而是真實可執行的程式碼——在 canvas 上。

它的運作方式：
- 把 GitHub repo clone 進來，或直接上傳本地資料夾到 Figma
- 程式碼作為可以執行的即時圖層落在你的 canvas 上
- 你的團隊可以評論它、用提示語修改它，或提取回設計圖層
- 在設計模式編輯，推回程式碼，推回 repo

設計和程式碼在同一個 canvas 上。同一個檔案。同一個團隊。

---

🔄 **Extract Designs 工作流程**

這是改變一切的功能：

1. 選取你的程式碼圖層
2. 選擇「Extract designs（提取設計）」——當前狀態轉換成可編輯的 Figma 圖層
3. 在設計模式調整視覺細節（顏色、字型、間距、狀態）
4. 一鍵把你的修改更新回程式碼圖層
5. 審查通過後推回 repo

以前：設計 → 規格 → 工程師重建 → 交接會議 → 重複
之後：直接在真實元件上設計 → 推出去 → 完成

---

💡 **為什麼這件事很重要（從系統角度）**

交接一直是資訊流失的地方：

- 設計師假設某些狀態會被建出來
- 工程師根據他們能從規格推斷的東西來實作
- 邊緣案例被遺漏

Code Layers 移除了這個推斷的步驟。你在真實的東西上設計。沒有什麼可以被誤解。

---

⚠️ **老實說的複雜性**

這不是免費的升級——它帶來了真實的治理問題：

1. **所有權** — 如果設計師修改了程式碼圖層，誰擁有那個 commit？
2. **審查流程** — 每次設計變更在推回 repo 前都需要工程批准嗎？
3. **範圍蔓延** — 有直接程式碼存取權的設計師可能意外破壞在設計模式看不到的東西
4. **團隊對齊** — 這只在設計與工程已經有強大共同流程時才能良好運作

如果你的團隊沒有清晰的協作協議，Code Layers 會立刻暴露那個缺口。

---

🎯 **誰應該申請 closed beta？**

最適合：
- 設計工程協作已經緊密的團隊
- 有健全 code review 流程的公司
- 設計師與工程師比例高的專案（每個設計師緊密配合 1-2 個工程師）

等 GA 再說的情況：
- 你的設計和工程團隊在不同部門工作
- 你們沒有既定的 PR review 慣例
- 你的 codebase 很大，對意外變更敏感

---

📌 **真正的新聞**

Figma Code Layers 不只是一個功能。

這是 Figma 的一個主張：canvas——不是 IDE——應該是設計和工程匯合的地方。

這對你的團隊是否正確，取決於你的組織是怎麼結構的，而不是這個工具本身。
