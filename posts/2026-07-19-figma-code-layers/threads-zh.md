# Threads — Figma Code Layers（繁體中文）
**格式：** 長篇個人思考，不加 hashtag，對話式語氣

我想了很多關於設計中「交接問題」（handoff problem）。

不是工具層面的那種——「怎麼乾淨地輸出規格」——而是結構層面的：設計和工程一直是兩條平行的軌道，朝著同一個產品前進，而交接是它們被迫同步的那一刻。每次同步都是一次翻譯。翻譯永遠會流失一些東西。

現在 closed beta 的 Figma Code Layers，是我見過最激進的嘗試——直接消滅翻譯這件事。

概念很直接：程式碼是 canvas 上的一種圖層類型。你把一個 repo clone 進來，它作為一個可以執行的圖層落在你的 canvas 上。你的隊友可以看它、留評論、用提示語對它做修改。你可以把它提取回可編輯的 Figma 設計圖層，調整視覺細節，把變更推回程式碼圖層，滿意了再推回 repo。

同一個產物。兩個團隊。同一個 canvas。

我不認為這對大多數團隊會是順暢的。光是治理問題就很嚴重——誰擁有在 Figma 檔案裡對程式碼圖層做的變更？在推回 repo 之前誰來審查？在設計工具裡進行的程式碼審查是什麼樣子的？這些不是 UX 問題。這些是組織問題。沒有花心思對齊設計工程協作模式的團隊，在發現 Code Layers 有用之前，會先覺得它一團混亂。

但對已經對齊的團隊，好處是真實的。交接那一刻不再是一次文件交換，而是一次 canvas 上的編輯。設計師可以直接在生產元件上工作——不是它的複製品，而是元件本身——這種精確度是任何規格文件都做不到的。

我一直在思考的是這背後的平台策略。如果工程師開始在 Figma 裡 review 程式碼，而不是在 GitHub PR 裡，Figma 就成了工程流程的基礎設施，不只是設計流程的。這大幅改變了 Figma 在整個工具鏈中的槓桿位置。

Canvas 吸收程式碼，不是一個功能。這是一個關於「事實來源應該在哪裡」的主張。

我真的不確定這個主張是否正確。但我會密切關注誰拿到 closed beta 的資格，以及他們建出了什麼。
